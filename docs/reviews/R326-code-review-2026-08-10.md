## Important Issues

### [I1] Enumeration Opener Regex Truncates Provisions (b)–(h)
- **File:** `app/engines/kg_context.py:467`
- **Bug:** `_ENUM_OPENER_RE` is compiled as `re.compile(r"(?:\(?a\)\s|\(?1\)\s|1\.\s)")`, strictly matching enumerations starting with `(a)`, `(1)`, or `1.`. If a provision unit starts with `(b)`–`(h)` or `(2)`–`(9)`, `_ENUM_OPENER_RE` fails to match.
- **Impact:** The budget extension to `_UNIT_HARD_CEILING` (2600 chars) fails to trigger for points (b) through (h) and numbered items past 1. This causes points (b)–(h) in Article 5(1) prohibited practices and Article 10 duties to be truncated mid-clause at 900 chars (`limit`), defeating the R325 enumeration preservation fix.
- **Suggested Fix:** Expand `_ENUM_OPENER_RE` to match any letter/digit enumeration opener:
  ```python
  _ENUM_OPENER_RE = re.compile(r"(?:\(?[a-hA-H1-9]\)\s|[1-9]\.\s)")
  ```
- **Confidence:** High (95%)
- **Found by:** Logic & Correctness, Contract & Integration

### [I2] Un-Synchronized Lazy Initialization of `_EXECUTOR` ThreadPoolExecutor
- **File:** `app/engines/kg_context.py:345-350`
- **Bug:** `_get_kg_executor()` lazily instantiates the module-level `_EXECUTOR` without synchronization (`threading.Lock()`).
- **Impact:** Under concurrent requests on cold start, multiple threads can observe `_EXECUTOR is None`, instantiating separate `ThreadPoolExecutor` instances and leaking worker threads.
- **Suggested Fix:** Protect lazy initialization with double-checked locking using a `threading.Lock()`:
  ```python
  _EXECUTOR_LOCK = threading.Lock()
  _EXECUTOR: ThreadPoolExecutor | None = None

  def _get_kg_executor() -> ThreadPoolExecutor:
      global _EXECUTOR
      if _EXECUTOR is None:
          with _EXECUTOR_LOCK:
              if _EXECUTOR is None:
                  from concurrent.futures import ThreadPoolExecutor
                  _EXECUTOR = ThreadPoolExecutor(max_workers=2, thread_name_prefix="kgctx")
      return _EXECUTOR
  ```
- **Confidence:** High (95%)
- **Found by:** Concurrency & State

### [I3] Parent Collapse Regex Bypassed on `Art.` Prefix or Arabic Annex Formats
- **File:** `app/routes/regenold.py:1280-1292`
- **Bug:** `_head(ref)` extracts the parent provision using `re.match(r"(Article\s+\d+|Annex\s+[IVXLCDM]+)", ref.strip())`. When references use `"Art. 27"` or `"Annex 3"`, `re.match` fails to match (`m` is `None`) and returns the full string untouched (`"Art. 27.1"`).
- **Impact:** Parent collapse (`REGENOLD_PARENT_COLLAPSE=1`) fails to drop parent head citations when sub-points are cited using standard `"Art."` prefix or Arabic annex formats.
- **Suggested Fix:** Update `_head` regex to accommodate `Art.` / `Article` and Roman/Arabic Annex numerals:
  ```python
  def _head(ref: str) -> str:
      m = re.match(r"((?:Article|Art\.?)\s*\d+|(?:Annex|annex_)\s*(?:[IVXLCDM]+|\d+))", ref.strip(), re.IGNORECASE)
      return m.group(1) if m else ref.strip()
  ```
- **Confidence:** High (95%)
- **Found by:** Error Handling, Logic & Correctness, Contract & Integration

### [I4] Arabic Annex Normalization & Fallback Blockade in Vector Recall
- **File:** `app/engines/vector_recall.py:20-26`, `116-138`
- **Bug:** `_norm_ref(r)` strictly matches Roman numerals (`[IVXLCDM]+`). Arabic annex hits (e.g. `"Annex 3"`) normalize to `"Annex 3"`, which fails validation against `ARTICLE_EXISTENCE` (`"Annex I"`...`"Annex XIII"`). Furthermore, checking `if not article_scores:` before calling local `embeddings_index` fallback causes local SVD fallback to be skipped if Neo4j returned unnormalized keys that were dropped during validation.
- **Impact:** Vector recall silently discards valid Annex candidates in Arabic numeral format and fails to fall back to `embeddings_index` when Neo4j keys get filtered out.
- **Suggested Fix:** Map Arabic numbers 1–13 to Roman numerals (`I`–`XIII`) in `_norm_ref`, and base fallback decisions on valid `ARTICLE_EXISTENCE` entries.
- **Confidence:** High (90%)
- **Found by:** Error Handling, Logic & Correctness

### [I5] Component D False-Positive Hallucination Flag on Arabic Annex Mentions
- **File:** `app/routes/regenold.py:9027-9071`
- **Bug:** Component D extracts prose citations using `re.finditer(...)`. When Stage-2 prose cites an annex using Arabic numerals (e.g. `"Annex 3"`), Component D fails to match `"Annex 3"` against `reference_bases` or `ARTICLE_EXISTENCE` (which use Roman numerals), incorrectly flagging `"Annex 3"` as a hallucinated citation (`has_hallucination = True`).
- **Impact:** Valid Stage-2 LLM answers citing `"Annex 3"` are discarded and forced into deterministic fallback.
- **Suggested Fix:** Normalize Arabic annex numbers to Roman numerals (`Annex 3` -> `Annex III`) when checking `reference_bases` and `ARTICLE_EXISTENCE` in Component D.
- **Confidence:** High (95%)
- **Found by:** Logic & Correctness
